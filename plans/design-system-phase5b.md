# Design system Phase 5b: admin moderation queues

## Goal / context
Second of three plans for Phase 5 (admin). Migrate every moderation queue behind the admin tabs (questions, correction proposals, FAQ answers, contentious points, Q&A answers, calls to action published and pending, contributor submissions, coverage, feedback, reviews and endorsements, brief proposals, waitlist) and the tab components that list them from the old tokens (`paper`, `ink`, `line`, `pink`, `blue`, `coverage`, `font-display`, `font-body`, stock `red-*`/`amber-*`/`green-*`/`blue-*`/`purple-*`/`pink-*`/`gray-*` colours, text under 12px) to the new design system. Source of truth: `docs/design/design-system/design-system.md` (3.1 Actions, 3.5 Data display: Accordion row, StatusChip, key-value rows; 3.6 Feedback; 3.7 Overlays: Confirm dialog; section 4 Patterns: Moderation and Destructive actions), `docs/design/design-system/migration.md` (token map) and `docs/design/design-system/migration-prompts.md` ("Standing rules" and the "Phase 5" prompt). Decision 4 (admin density): Inter 14px rows, 44px minimum interactive height, nothing under 12px. Decision 2: StatusChip may carry a tone on admin screens, always with icon and word.

Ordering and prerequisites: this is plan 2 of 3. Plan `design-system-phase5a` (PR 139: admin shell, tab row, applications) must be merged to `master` first, and the maintainer's local `master` must be fast-forwarded (`git fetch` then update `master`) BEFORE `plan run`: the 5a branch was once created from a stale local `master` and missed PR 138. Step 1 checks this. Plan 5c (analytics tab, any leftovers, final cleanup of admin) follows.

Facts checked 2026-11-18 on the 5a branch (non-blank lines / old-token hit lines; run the OLD grep again in step 1 because 5a changes some files):
- `app/admin/cards.tsx` after 5a keeps only `QuestionCard` (approve/dismiss, `loading` `approving|dismissing`), `CorrectionProposalCard` (approve/dismiss) and `BriefProposalCard` (props `proposal`, `briefOptions`; decline, convert to brief, link to an existing brief; the largest card, about 135 lines; button text "Working…" and "Decline"). It imports `formatDate`, `Field` from `./admin-shared`.
- Simple cards, one file each: `faq-answer-card.tsx` 71/10 (`FaqAnswerCard`), `question-answer-card.tsx` 70/10 (`QuestionAnswerCard`), `contentious-point-card.tsx` 68/8 (`ContentiousPointCard`), `content-post-card.tsx` 102/13 (`ContentPostCard`), `coverage-card.tsx` 117/12 (`CoverageCard`), `feedback-card.tsx` 56/6 (`FeedbackCard`), `review-card.tsx` 63/7 (`ReviewCard`, a "Remove from list" icon control with `aria-label` and `title`), `waitlist-card.tsx` 53/7 (`WaitlistCard`), `cta-card.tsx` 143/19 (`CtaCard` pending with approve/dismiss, `PublishedCtaCard`).
- Tab components: `tabs/simple-queues.tsx` 162/5 (`QuestionsTab`, `CorrectionProposalsTab`, `FaqAnswersTab`, `ContentiousPointsTab`, `QuestionAnswersTab`), `tabs/ctas.tsx` 73/5 (`CtasTab`), `tabs/content.tsx` 95/3 (`QuotesTab`, `CoverageTab`, `FeedbackTab`), `tabs/misc.tsx` 131/5 (`ReviewsTab`, `ProposalsTab`, `WaitlistTab`; `AnalyticsTab` and `analytics-tab.tsx` are 5c: leave them).
- Today every dismiss, decline and remove action is immediate (no confirmation): `handleDismiss` in each card, `handleDecline` in `BriefProposalCard`, `handleRemove` in `ReviewCard`. The Phase 5 prompt says destructive actions use a danger Button plus ConfirmDialog; these actions only change moderation state (the item leaves the queue), they do not delete user accounts. Decision: keep them immediate and non-danger (`Button variant="secondary"`), no new confirmations (no behaviour change), and say so in the final Done line. The one exception is the Application expanded-body "Reject" from 5a, which acts immediately while the quick reject asks first: step 2 makes both go through the same `ConfirmDialog`.
- Primitives in `components/ui`: `Button` (variants primary, rose, cobalt, secondary, ghost, danger; `small`, `icon`, `pending`, `fullWidth`), `ConfirmDialog`, `StatusChip`, `RoleLabel`, `Alert`, `EmptyState`, `Tag`, `Select`, `TextInput`, `Textarea`, `Field`, `Pagination` (already new), `icons.tsx` (`chevron-right`, `check`, `x`, `clock`).
- Tests: `tests/faq-answers.spec.ts` (about line 257) finds the ADMIN FAQ card with `ancestor::div[contains(@class, "border-line")]` and then clicks "Approve": it must be rewritten in the same step that migrates `faq-answer-card.tsx` (step 4), to a `data-testid` locator. `tests/two-ink-bold-11f-admin.spec.ts` was reworked in 5a; re-check it. `tests/ctas.spec.ts` may open the admin CTA queue: grep before step 6. No other spec asserts admin queue classes (verify in the last step).

Decisions made for this plan: all queue cards share ONE look, built once in step 2 from small shared pieces in `app/admin/admin-shared.tsx` (an accordion or flat row container, a key-value row, an action bar, an error `Alert`); individual cards then only supply content. Cards that have an expandable body use the same accordion row as `application-card.tsx` (read it first: chevron, `aria-expanded`, 44px summary, `border-rule bg-vellum`).

Non-goals: no logic, data fetching, route, copy or behaviour changes (note bugs in the final step's Done line); every admin server action keeps its `requireAdmin()` call untouched and `lib/` is not touched at all (do not edit `lib/admin/*`); `AnalyticsTab`/`analytics-tab.tsx`, `app/admin/briefs/**`, `AdminScreen.tsx`, `tab-button.tsx` and `app/admin/page.tsx` are not touched; do not touch `plans/.plan.json`, CI, ship settings or `<body>` styles.

Constraints for every step: Bun only (never npm, npx or node). Do NOT run Playwright (`bun run test`, `bunx playwright`): it would write throwaway rows to the real Supabase project; CI runs the suite. Verify with `bun run lint`, `bunx tsc --noEmit`, `bun run build` and greps. The runner has already copied the build env to `.env.local` in this worktree: run `bun run build` directly, never source or read env files. Edit files with the Write and Edit tools and `git mv`; avoid heredoc, `sed -i` and `cat a b > c` pipelines (unattended sessions cannot approve them). Lint baseline: 1 error in the generated `env.d.ts` and about 195 warnings from vendored `.claude/skills` and `.github/skills`; "lint clean" means no NEW problems in files you changed (`max-lines` warns at 500 non-blank non-comment lines). No em dashes in user-facing text or commit messages. Do not use the bare word "format" in commands or commit messages. Use only tokens and utilities from `app/app-theme.css` and primitives in `components/ui`: no raw hex, no stock Tailwind colours, no text under 12px (`text-[9px]`, `text-[10px]` are gone; use `text-label` or larger), min 44px touch targets, visible `focus-ring`. Old-token grep used below (call it OLD): `(text|bg|border|ring|fill|divide)-(ink|paper|line|pink|blue|coverage)|font-display|font-body|font-extrabold|bg-black|(bg|text|border|ring)-(gray|red|blue|green|amber|yellow|purple|pink)-[0-9]|text-\[(9|10|11)px\]`. Commit each step with a message with no em dashes and no bare word "format".

Lessons carried from 4a to 5a (CI failed on these before; apply in every step):
- Unexecuted specs fail in CI on old-UI assumptions: read the markup of every asserted element; avoid strict-mode multi-matches (scope locators, exact names); prefer `data-testid` over class or DOM-depth locators (`xpath=../..` in 5a was flagged); hover-only text is `display:none` (`toBeAttached`).
- A class string with a missing space silently drops a utility: grep changed files for fused utilities with `grep -nE "\][a-z]"` inside class strings.
- Keep each card's visible names (button labels "Approve", "Dismiss", "Decline", "Convert", etc.) exactly: specs and admins find them by name.
